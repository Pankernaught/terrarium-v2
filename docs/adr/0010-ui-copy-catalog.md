# Authored UI prose lives in one `copy.json` catalog, edited from Plant Admin

Every editable sentence the app shows — screen copy, build-guide steps, and the
compatibility/verdict warnings — moves out of source into a single flat
`key → text` catalog ([src/data/copy.json](../../src/data/copy.json)), read
through `copy(key, slots?)` ([src/lib/copy.ts](../../src/lib/copy.ts)). The
Curator rewords prose in a new **Copy** tab in Plant Admin (ADR 0005) instead of
editing `.tsx`/`.ts` in an IDE. Only the *wording* moves; the logic that selects
a message and computes its values stays in code.

## Context

Prose was scattered as string literals across ~10 files: static screen copy and
alert titles in the seven screens, and — the bulk of it — the build-guide
instructions ([guide.ts](../../src/logic/guide.ts)) and the pairwise/group
warnings ([compatibility.ts](../../src/logic/compatibility.ts),
[verdict.ts](../../src/logic/verdict.ts)). Plant descriptions and glossary
definitions were already editable via Plant Admin; this prose was not, so a
wording tweak meant an IDE round-trip through code.

The prose is not uniform. Three shapes:

1. **Static strings** — `"All quiet for now"`, a sealing instruction.
2. **Templates with holes** — `"Add {depth} of {material} to the bottom."`,
   `"{a} needs {aLight} light … will cook shade-adapted plants — lethal."` The
   sentence is fixed; the app fills the numbers, names, and levels at runtime.
3. **Branch-selected** — which of five light-conflict messages fires is decided
   by `lights.has('direct')`, severity tiers, etc.

The naive reading of "fold all the prose into the tool" is to capture shape 3 in
data too — a conditional/templating engine driven from JSON. That rebuilds the
compatibility/guide engines inside an admin form and is rejected outright.

## Decision

1. **One flat catalog, dotted keys.** `copy.json` is a flat `key → string` map
   (`"guide.drainage"`, `"compat.light.lethal"`). Flat (not nested) so
   `keyof typeof copy.json` gives the helper a literal key union for free, and
   the tab renders a flat editable list. No `schemaVersion` — it would pollute
   the key type and the catalog never needs migration (it's not a payload).

2. **`copy(key, slots?)` with dumb `{slot}` substitution.** The helper looks up
   the string and string-replaces `{name}` placeholders the caller supplies. Keys
   are typed against the JSON, so a typo or renamed entry fails `tsc`, not the
   device — this is the only safety net for the screens, which have no prose tests.

3. **Wording moves, logic stays.** Each literal becomes a `copy(...)` call;
   branch selection and value computation are untouched in `guide.ts` /
   `compatibility.ts` / `verdict.ts`. The line is: the catalog owns the sentence,
   the code owns *which* sentence and *what fills it*. We reject moving shape-3
   branching into data (a template engine in JSON) — it duplicates the engine and
   buys nothing the author can't do by rewording the per-branch entries.

4. **Runtime exception text is not catalogued.** `err.message` in
   `Alert.alert('Backup failed', …)` is generated by the OS/exception at runtime,
   not authored — there is nothing to put in the catalog. The *title* is
   catalogued; the body is left as-is.

5. **Reuse Plant Admin, don't build a second tool.** Per ADR 0005 the tool
   already has the local server, the read/write plumbing, and the editing UI. The
   Copy tab is a third entity alongside Plants/Terms, with its own minimal
   edit-only view ([index.html](../../tools/plant-admin/index.html)) rather than
   the slug'd-record machinery, plus `GET`/`PUT /api/copy`
   ([server.js](../../tools/plant-admin/server.js)). A standalone tool would
   re-implement all of that.

6. **The Copy tab is edit-only.** Keys are wired to code, so the tab rewords
   existing entries and never adds or deletes them — a new key would be dead data,
   a deleted key would break `tsc`. The `PUT` enforces this (rejects unknown keys).

## Consequences

- **Helper uses relative imports.** `src/lib/copy.ts` imports `../data/copy.json`
  and logic imports `../lib/copy`, because the vitest config resolves no `@/`
  alias ([vitest.config.ts](../../vitest.config.ts)); screens use `@/lib/copy`.
- **The existing engine tests are the proof.** `compatibility`/`verdict`/`guide`
  tests assert exact prose with `toBe`/`toContain`, so the refactor is verified
  byte-identical by the suite staying green — plus a small
  [copy.test.ts](../../src/data/__tests__/copy.test.ts) guarding substitution.
- **`copy.json` is written dense.** The `PUT` writes plain `JSON.stringify(…, 2)`,
  so the blank-line grouping in the authored file collapses on first save. A
  byte-exact serializer (as plants.json/glossary.json have) was rejected — copy
  is a new file with no external format contract, and grouping stays visible in
  the tab (group headers) and by key prefix.
- **Templated entries carry a contract.** An entry like
  `"{a} needs {aLight} … — lethal."` must keep its `{slots}` or the rendered
  string breaks; the tab surfaces a per-entry "keep these placeholders" reminder,
  but nothing enforces it. Rewording is now a non-engineer action with an
  un-checked failure mode — accepted for a single-author tool.
- **Not exhaustive.** A few sibling strings (e.g. dynamically-pluralised bodies,
  one-word button labels) were deliberately left in code; the catalog is for
  sentences worth rewording, not every visible token.
